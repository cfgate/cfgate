# v0.3.0-alpha.1 Development Spec

This document is the final-state implementation contract for continued `v0.3.0-alpha.1` development. It records the docs-first spec, implementation sequence, and test plan for the current OriginPolicy, BackendTLSPolicy, origin CA, Gateway API, and cloudflared-h2c work.

## Scope

`v0.3.0-alpha.1` closes the gap between cfgate's Kubernetes-facing Gateway API model and the remote Cloudflare Tunnel configuration consumed by cloudflared.

In scope:

- `CloudflareOriginPolicy` as the cfgate-specific origin policy API for `HTTPRoute` targets.
- Gateway API `BackendTLSPolicy` runtime interop for Service backend TLS validation.
- Managed origin CA pool references on `CloudflareTunnel`.
- Generated CA Secrets and cloudflared mounts for cross-namespace origin CA data.
- Route annotations as the final alpha-line override surface.
- Accepted-route-only Cloudflare ingress rule emission.
- cloudflared-h2c fork pinning and h2c origin transport validation.
- Unit, optional contract, and user-run e2e coverage for the cfgate/cloudflared-h2c boundary.

Out of scope:

- New CRD fields beyond PR #72.
- GRPCRoute, TCPRoute, and TLSRoute public-hostname support.
- Running live Cloudflare e2e during automated agent implementation.
- Changing upstream cloudflare/cloudflared.

## Existing PR #72 Changes

PR #72 is the active development base for this release. It currently adds or changes:

- `CloudflareOriginPolicy` API, CRD, RBAC, samples, docs, status, and runtime application.
- `CloudflareOriginPolicy` target resolution for Gateway API `HTTPRoute` targets.
- Policy conflict handling using Gateway API policy precedence.
- Gateway API `BackendTLSPolicy` controller support and runtime interop.
- Backend TLS CA ConfigMap materialization into generated cloudflared-mounted Secrets.
- `CloudflareTunnel.spec.originCAPools` for named managed origin CA pools.
- Cross-namespace origin CA Secret handling with Gateway API `ReferenceGrant`.
- Managed and unmanaged route annotation modes for `originRequest.caPool`.
- Route annotation support for origin protocol, Host header, SNI, TLS verify, HTTP/2, h2c, timeout, and CA pool selection.
- Cloudflare Tunnel remote configuration sync that preserves SDK-unknown h2c fields.
- Runtime sync paths that react to origin policy, BackendTLSPolicy, Secret, and ConfigMap changes.
- cloudflared fork image bump work for h2c-capable default deployments.

## Final Runtime Contracts

### Gateway API To Cloudflare Config

Only accepted `HTTPRoute` rules emit Cloudflare Tunnel ingress rules. A route is accepted for emission only when:

- Its parentRef targets a cfgate-managed Gateway.
- Its sectionName, when present, matches an HTTP or HTTPS listener.
- Its route hostnames are accepted by the listener hostname.
- The listener `allowedRoutes.namespaces` policy allows the route namespace.
- Its backendRefs are supported Service references.
- Cross-namespace backend Service references are allowed by `ReferenceGrant`.

Rejected routes do not block valid sibling routes.

### Config Hash And Connected Route Count

The Cloudflare remote config hash is computed from emitted config only. Rejected or skipped routes do not contribute.

`CloudflareTunnel.status.connectedRouteCount` counts emitted Cloudflare ingress rules, not raw HTTPRoute objects or parentRefs.

### Origin Runtime Composition

Origin settings apply from lowest to highest precedence:

1. `CloudflareTunnel.spec.originDefaults`
2. accepted `CloudflareOriginPolicy`
3. accepted `BackendTLSPolicy`
4. HTTPRoute annotations

Annotations preserve field presence. Therefore `false`, `0`, and `no` can explicitly disable inherited booleans. v1alpha1 CRD bool fields remain enable-only because Kubernetes defaulting cannot distinguish omitted from false.

### h2c Validity

`h2cOrigin` is valid only for cleartext HTTP origin services.

Invalid combinations:

- `h2cOrigin` with `http2Origin`.
- `h2cOrigin` with `origin-protocol: https`.
- `h2cOrigin` with generated `https://` service URLs.
- `h2cOrigin` with generated `wss://` service URLs.
- `h2cOrigin` with BackendTLSPolicy on the same backend.
- `origin-protocol: http` on a route with BackendTLSPolicy on the same backend.

`http2Origin` is the HTTPS-origin HTTP/2 option. `h2cOrigin` is the cleartext HTTP/2 option.

### BackendTLSPolicy HTTPS Behavior

When accepted, BackendTLSPolicy makes cfgate connect to the backend with HTTPS. It sets origin server name from `spec.validation.hostname` and maps supported CA ConfigMap data into a managed cloudflared `caPool` path. `wellKnownCACertificates: System` uses system trust and no `caPool` override.

HTTPRoute annotations apply after BackendTLSPolicy only for compatible fields. They cannot override the BackendTLSPolicy HTTPS requirement.

### ReferenceGrant Requirements

Gateway API `ReferenceGrant` is required for:

- Cross-namespace `CloudflareOriginPolicy` targetRefs.
- Cross-namespace HTTPRoute backend Service references.
- Cross-namespace origin CA Secret references from `CloudflareTunnel.spec.originCAPools`.

The grant lives in the target namespace.

### cloudflared-h2c Fork Version Policy

cfgate defaults to the inherent-design cloudflared fork because upstream cloudflared does not support `h2cOrigin`.

Target default for this release is `ghcr.io/inherent-design/cloudflared:2026.5.1-h2c.2` unless Phase 2 needs a production fork change. If the fork changes, cfgate must pin the new released fork tag.
